# D1 / database layer audit

**Status: all 7 findings fixed** (2 × P1, 2 × P2, 3 × P3). No P0.

Each finding was deleted from this file as it was closed. What remains below is the standing analysis — index coverage, the full query list, row-read cost and quota headroom — updated to the fixed state, so a future audit starts from facts rather than re-deriving them.

**Planners used:** primary = local D1 via `wrangler d1 execute rcnsh --local` (miniflare, real schema); scale cross-check = `sqlite3` 3.50.6 on a scratch DB built from `migrations/*.sql` seeded to 140,000 guestbook / 20,000 session rows. Every plan was identical at both sizes.
**Billing evidence:** `rows_read` numbers came from `wrangler d1 execute rcnsh --remote` `meta` on production (read-only `SELECT`s only; 10 guestbook rows, 1 session row at the time).

## What changed

| Was | Fix |
|---|---|
| P1 — `getStats()` ran `SCAN` + `USE TEMP B-TREE FOR GROUP BY`, billed at 2N because `country` had no index | `migrations/0005_guestbook_country_index.sql` + `schema.ts`. Plan is now `SCAN guestbook USING COVERING INDEX guestbook_country_idx`, verified locally; the temp b-tree is gone and the cost halves to N. Still O(N) — a roll-up table is the durable answer if the table ever gets large. |
| P1 — `/api/guestbook/delete` invalidated both cache keys unconditionally, so a signed-in caller could put the O(N) scan back on the anonymous read path 120×/min at no cost to themselves | `if (result.meta.changes > 0) await invalidate()`. A delete that removed nothing cannot have made anything stale. The KV write amplification (240 writes/min ≈ 10.4M/month against a 1M allowance) goes with it. |
| P2 — `/api/guestbook/list` was uncached and anonymous: exactly 26 rows a call, 120/min ≈ 4.49M rows/day per IP per colo | Cache API wrapper keyed on the *re-encoded* cursor, 60s TTL matching `FRESH_SECONDS`. Junk cursors collapse onto the page-1 key rather than minting an entry each, so the cache cannot itself become the amplifier. Verified: a row inserted between requests does not appear, i.e. D1 is skipped. |
| P2 — infinite scroll cost O(table size) per reader, not O(page size) | No query change — it was already optimal. Fixed by the cache above: deep pages are now shared between readers. `PAGE_SIZE` left at 25. |
| P3 — sessions were swept only when somebody logged in | Sampled from `getSession` (~1 signed-in request in 50) and fired through `waitUntil`, so it runs after the response and no caller waits on it. A Cron Trigger was the tidier shape and is not available: `@astrojs/cloudflare` registers with `entrypointResolution: "auto"` and generates `{ fetch: handle }`, with no hook for a `scheduled` export — so a real cron would have meant a second Worker for one `DELETE`, or patching the adapter's build output. Both were disproportionate to a table holding a handful of rows. |
| P3 — `createSession` made two sequential D1 round trips inside the OAuth callback | The sweep left `createSession` entirely, so the second trip is gone rather than batched. Batching would have wrapped both in a transaction, letting an opportunistic sweep failure roll back a real session insert — the wrong trade. |
| P3 — replaying `0002` silently duplicated 13 rows, and `meta/0004_snapshot.json` was missing | `0002` rewritten as `INSERT … SELECT … WHERE NOT EXISTS` on `(github_id, created_at)`. Replaying every migration now leaves 13 rows and no duplicates, verified. `0004`'s snapshot backfilled and `0005` generated by drizzle-kit, so the chain is intact 0000→0005 and `drizzle-kit generate` reports no drift. The file was **not** renumbered — `d1_migrations` records it by name, so it stays skipped wherever it has already run. |

**Not changed, deliberately:** no `WRITE_BUDGET` rate-limit bucket for guestbook mutations. The conditional invalidate removes the amplification at its root, which makes a second budget redundant defence costing an account-wide namespace id.

## 1. Index coverage

### `guestbook`

Indexes that exist (`migrations/0000_init.sql:12-13`, `migrations/0001_guestbook_multiple_messages.sql:2`, declared at `src/lib/db/schema.ts:26-30`):

| Index | Columns |
| --- | --- |
| *(rowid)* | `id` — `INTEGER PRIMARY KEY AUTOINCREMENT` |
| `guestbook_created_at_idx` | `(created_at)` |
| `guestbook_github_id_created_at_idx` | `(github_id, created_at)` |

`guestbook_github_id_unique` on `(github_id)` was dropped in `0001`.

Every predicate the application issues against it:

| Predicate | Source | Supporting index | Plan |
| --- | --- | --- | --- |
| `ORDER BY created_at DESC, id DESC LIMIT 26` | `src/lib/guestbook.ts:92` | `guestbook_created_at_idx` | `SCAN … USING INDEX` (ordered walk, no temp b-tree) |
| `WHERE created_at < ? OR (created_at = ? AND id < ?)` + same `ORDER BY`/`LIMIT` | `src/lib/guestbook.ts:92` | `guestbook_created_at_idx` | `SEARCH … (created_at<?)` |
| `GROUP BY country` | `src/lib/guestbook.ts:134` | `guestbook_country_idx` | `SCAN … USING COVERING INDEX` |
| `WHERE github_id = ? ORDER BY created_at DESC LIMIT 1` | `src/lib/guestbook.ts:175` | `guestbook_github_id_created_at_idx` | `SEARCH … USING COVERING INDEX` |
| `WHERE id = ? AND github_id = ?` (DELETE) | `src/pages/api/guestbook/delete.ts:24` | rowid | `SEARCH … USING INTEGER PRIMARY KEY` |
| `INSERT` | `src/pages/guestbook.astro:89` | — | 3 rows written (table + 2 indexes) |

Every predicate is now covered. `country` was the one gap; `migrations/0005` closed it.

The `ORDER BY created_at DESC, id DESC` tiebreak needs no `(created_at, id)` index: `id` is `INTEGER PRIMARY KEY`, so it *is* the rowid, and SQLite's index entries are already `(created_at, rowid)`. That is why no `USE TEMP B-TREE FOR ORDER BY` appears. Verified against the planner at both 14 and 140,000 rows.

## 3. Row-read cost per request

`rows_read` figures marked **(measured)** come from production `meta`. `N` = guestbook row count (10 today).

| Route | D1 work | Today (N=10) | 10× (N=100) | 100× (N=1,000) |
| --- | --- | --- | --- | --- |
| `GET /guestbook`, anonymous, KV warm | none | 0 | 0 | 0 |
| `GET /guestbook`, anonymous, KV cold/busted | `getPage` + `getStats` | 26 + 20 = **46** | 26 + 200 = 226 | 26 + 2,000 = **2,026** |
| `GET /guestbook`, signed in, KV warm | `getSession` + `lastPostedAt` | 2 | 2 | 2 |
| `POST /guestbook` (accepted) | session + `lastPostedAt` + insert + re-read after invalidate | 2r + 3w + 46r | 2r + 3w + 226r | 2r + 3w + 2,026r |
| `GET /api/guestbook/list?after=…` | `readPage(cursor)`, **never cached** | **26 (measured, LIMIT-bound)** | 26 | 26 |
| `POST /api/guestbook/delete` | `getSession` + scoped delete + **unconditional** cache drop | 1r + 0–3w, then 46r on the next `/guestbook` | 1r, then 226r | 1r, then 2,026r |
| `GET /api/auth/callback` | insert session + expiry sweep | 3w + 3k | 3w + 3k | 3w + 3k |
| `POST /api/auth/logout` | delete by PK | 1r + 3w | 1r + 3w | 1r + 3w |
| A reader who scrolls to the bottom | `ceil((N−25)/25)` uncached `/api/guestbook/list` calls | 0 extra | 3 calls / 78 rows | 39 calls / **1,014 rows** |

**Scales with table size rather than page size:** `getStats` only, now `O(N)` rather than `O(2N)`, and behind a 60-second KV entry. The infinite-scroll walk is still `O(N)` in *calls* per reader, but the edge cache means those calls are shared rather than paid per visitor. Everything else is constant.

**Not present:** no `OFFSET` pagination, no `COUNT(*)` over the whole table outside `getStats`, no N+1 query loop, no query missing a `LIMIT` except `getStats` and the session sweep (both intentional aggregate/range operations). The sweep is sampled from `getSession` and fired via `waitUntil`, so it never delays a response.

## 4. Quota risk

D1 limits (Cloudflare docs, `workers/platform/pricing`, retrieved this session):

| | Workers Free | Workers Paid |
| --- | --- | --- |
| Rows read | 5 M/day (**enforced with hard query failures since 2026-09-01**) | 25 B/month included, then $0.001/M |
| Rows written | 100 k/day | 50 M/month included, then $1.00/M |

`docs/abuse.md` states the account is on Workers Paid, so the read ceiling that matters is 25 B/month.

Budgets from `wrangler.jsonc`, spent in `src/lib/throttle.ts:95-99` from the middleware **before** `next()`:

- `API_BUDGET` 120/min — covers `/guestbook`, `/api/guestbook/*`; **this is the budget in front of every D1 read**
- `SCAN_BUDGET` 40/min — `/api/files/search` only, touches no D1
- `AUTH_BUDGET` 10/min — `/api/auth/*`, the only unauthenticated D1 *write* path

All three are keyed on `cf-connecting-ip` and counted **per Cloudflare location**, so a distributed caller multiplies its allowance by however many colos it reaches. `throttle()` also fails open on any error (`src/lib/throttle.ts:100-103`). Both properties are documented and deliberate; they are the reason the WAF rule in `docs/abuse.md` matters, and they bound the ceilings below only for a single-host caller.

**Can a determined caller blow the budget?** (post-fix)

- *Anonymous, reads:* no longer meaningfully. `/api/guestbook/list` sits behind a 60-second edge cache keyed on the re-encoded cursor, so a flood of repeat requests costs zero D1 rows after the first. The worst case is one D1 read per distinct cursor per minute, and the cursor space is bounded by rows that actually exist rather than by what the caller sends.
- *Anonymous, writes:* no. The only unauthenticated write is the OAuth session insert, which needs a valid single-use GitHub code and is capped at 10/min.
- *Signed in, reads:* closed. `/api/guestbook/delete` only invalidates when it removed a row, so a caller hammering it with foreign or nonexistent ids no longer drops the cache — the amplification is gone at its root rather than rate-limited.
- *Unbounded row growth:* guestbook is capped at 1 message per signer per day (`src/lib/rate-limit.ts:7`), so it grows at most `users/day`. Sessions are swept off the response path from `getSession`, sampled at ~1 request in 50, so cleanup tracks traffic rather than logins.
- *Migration re-run safety:* the three DDL migrations still fail loudly on replay, which is the desired behaviour. `0002` and `0004` are both idempotent now — replaying every migration leaves the table at 13 rows with no duplicates.

**Residual, accepted:** all three rate-limit budgets are keyed on `cf-connecting-ip` and counted per Cloudflare location, so a distributed caller multiplies its allowance by the number of colos it reaches, and `throttle()` fails open on error. Both are deliberate and documented; the WAF rule in `docs/abuse.md` is what covers the distributed case.
