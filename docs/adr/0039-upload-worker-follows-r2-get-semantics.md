# 0039. Both readers of bucket bytes follow R2's get semantics

`workers/upload/src/handler.ts` and `/api/files/download` both read through `readObject` (`shared/bucket-http.ts`), which passes the request's Range and conditional headers to R2 `get()` and says what to answer; each reader only turns that into its own response.

R2 throws on a range it cannot satisfy, so a `get` error with a Range header answers 416, and without one it rethrows as a real failure. R2 returns an object without a body when a request condition fails, so that answers 304 if `if-none-match` or `if-modified-since` was sent, else 412. A 206 with `Content-Range` is sent only when the request carried a Range header, because `object.range` being set does not mean only part was asked for; this follows Cloudflare's own R2 Worker example.

`span()` (`shared/bucket-http.ts`) turns `object.range` into the bytes served, and `/api/files/download` uses it too, so both answer a suffix range (`bytes=-N`) with the last N bytes and a matching `Content-Range`. It checks range fields with `typeof`, not `in`. R2 returns every range field, unset ones as undefined, so `in` is always true, and a suffix range read as an offset would claim to start at byte 0.

Both readers decide a Range header with the helpers in `shared/bucket-http.ts`, so they answer it alike. `rangeToAsk` hands R2 a header only when it is one valid `bytes` range, rewritten in lowercase with its bounds normalised; a multi-part, reversed, other-unit or malformed header reaches R2 as no range at all and the whole object is served, as RFC 9110 asks. `rangeOutcome` then picks 200, 206 or 416 from the header and the object R2 returned, and a 416 always names the size (`bytes */size`) and carries none of the object's own headers. Only R2's own range refusal (10039) becomes a 416; any other R2 error surfaces. Bounds are capped at `LARGEST_OBJECT` (2^43 bytes), above R2's 5 TiB object limit: an end past it means "to the end", a suffix past it is the whole object, and a start past it can match no object, so it reaches R2 as no range and is refused with the body cancelled unread (after R2's preconditions). Keep the cap at or above R2's largest object, or valid ranges on large files are refused or rewritten.

R2 does not evaluate `If-Range`, so `readObject` does, after the other preconditions and against the object R2 actually returned, as RFC 9110 orders it. `ifRangeHolds` accepts only the object's strong ETag. A date is never accepted, because two uploads in the same second share one, and a 200 is always safe where a wrong 206 corrupts the client's copy. When it fails, the Range header is ignored entirely: a slice R2 already sent is cancelled and the whole object is fetched again for a 200, and a range that would have been a 416 is a 200 too. When R2 refuses a range, the object is fetched again without one, with the same conditions, so a failed condition still answers 304 or 412 before any 416, and the 416 names the size of the version it checks. Checking the returned object, never a separate `head()`, means a 206 is only ever a slice of the version the client named. A 304 from `/api/files/download` carries the same rewritten `Content-Type`, `Content-Disposition` and sandbox CSP as its 200, because a cache replaces its stored headers with a 304's.
