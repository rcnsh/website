# 0022. Route cache windows follow the cache layer behind them

A route's browser and edge window sits in front of whatever cache its data comes from. Where a loader keeps a KV window, the route's `max-age` is derived from the loader's constant in the `policies` table (`src/lib/http.ts`): `nowPlaying` from `CACHE_SECONDS` in `now-playing.ts`, `guestbookList` from `FRESH_SECONDS` in `guestbook-cache.ts`. The two layers cannot drift.

The other entries are set against their own layer. `/now.svg` is `publicFor(30, { swr: 60 })` because GitHub's image proxy (camo) may keep it that long; the snapshot behind it (`SNAPSHOT_FRESHNESS`, 15s, in `src/pages/now.svg.ts`) refreshes faster. Files list, meta and search responses are `publicFor(60)` while the bucket tree behind them is cached in KV for `TREE_FRESH_SECONDS` (300s, `src/lib/bucket.ts`). `/api/spotify/top` gets `publicFor(900)`, a ceiling rather than the range's KV freshness: its KV windows run to 24h and `cached()` serves stale past them, so deriving `max-age` from them would let the browser keep an already-old copy as long again. Thumb objects are written to R2 with `thumbObject`, `publicFor(86400)`, in their metadata, because upload.rcn.sh serves the stored header and a thumb belongs to one upload of its source, so it never changes in place.
