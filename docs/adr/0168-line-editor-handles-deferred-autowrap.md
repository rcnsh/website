# 0168. The line editor accounts for deferred autowrap

Terminals defer autowrap: a line that exactly fills its last row leaves the cursor parked on that row's last column rather than on the next row. When the prompt width plus the line length is an exact multiple of the column count, `draw()` in `src/lib/line-editor.ts` emits a CRLF to step onto the next row, so the row and column arithmetic used to restore the caret stays right. `leave()` does not add another, which would leave a blank row.

Columns are counted by cell width, not by code point. `cellWidth()` in `src/lib/cell-width.ts` gives East Asian Wide and Fullwidth characters and emoji with emoji presentation two columns and everything else one, matching how wterm lays out cells; wterm exports no width function of its own. A wide character that would start in a row's last column wraps whole to the next row, leaving that column empty, so `layout()` skips it when it sums widths. In a one-column terminal every character takes one column, as wterm draws a wide one there as a space.

`begin(prompt, width)` redraws from the top row of the line drawn last, so a line left mid-edit with output printed above it is redrawn in place rather than duplicated. After `leave()`, `commit()`, `abandon()` or `cleared()` the top row is the cursor's own. The prompt's printed width is passed separately from the prompt string, because the prompt may contain colour escape sequences and its string length is not its width.

`src/lib/line-editor.test.ts` tests the editor against a minimal screen model that implements deferred autowrap as xterm does, plus CR, LF, cursor up and forward, erase-below, and two-column cells that wrap whole. Wrapped-line redraw bugs show only when the output is replayed onto a grid with the real terminal's deferred-wrap semantics, and that subset is the behaviour the editor relies on.
